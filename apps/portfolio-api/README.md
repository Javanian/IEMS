# Owned portfolio CRM API

## K2b1 received component installation

New WOs can opt in with `installationRequired` alongside serialized output, lot genealogy and received serial custody. Operators explicitly bind already-consumed received identities to outputs from the same WO, record process-loss identities, and finalize exact identity and lot reconciliation. Source inventory stays CONSUMED. Removal permanently quarantines the installation disposition and leaves the parent incomplete. First shipment freezes the entire finalized installation revision; shipment sources, movements and units retain its immutable pointer.

Read the [K2b1 contract](../../checkpoints/wave4k2b1/CONTRACT.md) and [continuation plan](../../checkpoints/wave4k2b1/DEVELOPMENT-PLAN.md). Manufactured-component ownership/custody, general graph-cycle acceptance, replacement/rework, POD and full original E01 remain open. Supplemental incoming serial fixtures do not change canonical E01.

## K2a received serial custody

Untouched serialized receipts can be explicitly adopted into received identity custody. Required WOs opt in with `serialized`, `genealogyRequired` and `serialCustodyRequired`; operators claim exact identities while PLANNED, release reserves them, and the first operation consumes them with the existing stock movement. Claim and abandon do not change quantities. Adopted receipts permanently reject quantity-only reservation and counting; whole transfer requires all identities available and no holds. Existing untracked receipts retain their prior behavior.

Read the [K2a contract](../../checkpoints/wave4k2a/CONTRACT.md), [handoff](../../checkpoints/wave4k2a/HANDOFF.md) and [executed status](../../checkpoints/wave4k2a/STATUS.md). Received custody through WO consumption does not prove per-output installation, manufactured-child inventory, unique parents or cycle prevention; those remain K2b. No automatic promotion of previously consumed stock is supported.

## Wave4k K1 consumed-lot attribution

Planning can explicitly require per-output lot genealogy with `serialized: true` and `genealogyRequired: true`. Scoped genealogy commands attribute already-consumed materials, reconcile exact per-unit ratios and explicit process losses, and retain immutable revisions. Dedicated read/record/finalize capabilities are separate from existing manufacturing roles. First shipment freezes the whole work order's finalized revision; every new shipment still checks current whole-receipt holds. Legacy planning and shipment remain compatible when not opted in.

See the [wire contract](../../checkpoints/wave4k/CONTRACT.md), [handoff](../../checkpoints/wave4k/HANDOFF.md) and [executed acceptance status](../../checkpoints/wave4k/STATUS.md). This is lot attribution, not component-serial custody/installation, POD or full E01 acceptance. No additional material is consumed by attribution.

## Wave4g bounded fixture VAT contract (v1)

Commercial quote create/revisions additionally accept `taxPolicy: "FIXTURE_VAT_11_V1"` with existing `roundingPolicy: "LINE_HALF_UP"`. This is an explicit, fixed 11% canonical-fixture policy, not jurisdiction discovery, a current statutory rate, tax-inclusive pricing, exemptions or a general tax engine. No request rate overrides are accepted. `NO_TAX` retains its existing response shape and arithmetic.

VAT revisions and their frozen approval/SO snapshots expose currency-scale decimal strings `netAmount`, `taxAmount`, `grossAmount`, `taxRate: "0.11"`, `taxPolicyVersion: 1`; `total` means gross. Per-line amounts use HALF_UP extended net, then HALF_UP 11% of that rounded net; header amounts sum lines. R1 10 UN at USD12800.00 = 128000.00/14080.00/142080.00; R2 at12250.00 = 122500.00/13475.00/135975.00. Approval and conversion continue to pin the selected latest revision; revisions cannot mutate converted orders.

Shipment-backed VAT invoices inherit policy only from the approved SO snapshot, never from caller tax fields. Each line bills the difference between cumulative rounded net/tax/gross before and after its SO-line invoiced quantity. Tax is HALF_UP(rounded cumulative net *11/100); gross=net+tax. This conserves minor-unit rounding across arbitrary partials (including zero deltas). `amount` remains line net; `total`, outstanding and settlement use gross. VAT invoice headers/lines add `netAmount`, `taxAmount`, `grossAmount`; `sourceVersion` is the frozen SO version and `quoteRevision` the approved quote revision. VAT line rounding records also pin before/after tax/gross, source version and policy version.

`GET /api/fulfillment/orders/:id/entitlement` (fulfillment.read, scoped) returns one snapshot-consistent view of authorized/billed/remaining net, tax and gross per line and header, derived from the immutable SO pricing and transactional invoiced-quantity tallies. No milestone/credit-note entitlement is implied. Existing CAS, shipment caps, authorization, transaction audit/outbox and historical-key replay apply. Posted financial content is immutable through mounted API; settlement changes payment state/version only, not issued pricing. Privileged direct DB writers are outside this guarantee.

Tax quote/invoice document source and issue endpoints return **422 TAX_PDF_UNSUPPORTED** before rendering or publishing. The document-rendering package is unchanged; VAT PDF integration is a follow-up, never a NO_TAX fallback. Procurement and repair billing remain NO_TAX-only/out of this slice. This is bounded E01 monetary parity, not full E01, migration or production tax compliance.

## Wave4d corrective held-stock eligibility

New manufacturing material reservation through both `POST /api/manufacturing/work-orders/:id/release` and `/release-engineering`, and material consumption by the first `/record`, reject a receipt with `held === true`, `hold.active === true`, or nonzero decimal-string `heldQuantity` with **409 STOCK_ENCUMBERED**, matching the WMS hold representations. Any nonzero held quantity blocks the entire selected receipt; this is not partial held-balance allocation. False/inactive/zero markers remain eligible subject to existing state, UOM, quantity, version and authorization rules.

The checks run on scoped persisted receipts inside the same snapshot/majority transaction as receipt CAS writes, WO snapshot/records, material movements, manufacturing keys, audit and outbox. A concurrent receipt hold write contends with that actual receipt write even when it does not increment receipt version. A hold committed before material use blocks that use; an operation serialized before a later hold is not retroactively undone. A hold added after reservation blocks first consumption without cancelling the WO, releasing material, changing its frozen engineering/routing snapshot, or changing prior reservations. There is no hold administration, release/cancellation lifecycle, automatic remediation, or privileged direct-writer immutability guarantee. Subsequent operation records do not consume material again; this is a material-eligibility gate, not a new whole-WO suspension lifecycle.

An identical previously committed release/record key still returns its original response without effects after a hold, but only after current scope/session/role authorization. A rejected attempt persists no key or other transactional effects. Exact submitted engineering BOM strings, computed BigInt decimal quantities, currency and UOM contracts are unchanged. No full manufacturing parity or cutover is claimed.

### Integration consistency protocol (not cross-transaction atomicity)

The renderer owns an independent transaction. API transaction 1 fences authorization and the source, then persists a unique `documentIntents` PREPARED entry containing the server snapshot and authorization provenance. Renderer issuance then commits independently using its public API. API transaction 2 rechecks current permissions and publishes READY plus one `documentAudit` and one PENDING `documentOutbox` event atomically. Only READY intents are readable through this API. A renderer failure leaves a durable PREPARED intent; finalization failure may leave a private renderer artifact. Identical authorized retries resume that pinned snapshot and finalize once. Revocation before finalization denies publication; an unfinalized renderer artifact is not exposed. There is no worker, broker, background reconciliation, garbage collection or claim that these independent commits are atomic. Direct privileged database writes are outside this boundary. Source documents must only be mutated through fenced API transactions.

### Additive repair billing contract

Existing repair routes and response shapes remain available. `POST /api/repair/cases/:id/bill` `{expectedVersion,idempotencyKey}` requires `repair.bill`; accepted READY_FOR_RETURN/RETURNED cases produce one FINAL invoice from the accepted frozen scope, applying each stored deposit once. Response is the updated case with `finalInvoiceId`; invoice GET is unchanged. Deposit acceptance requires `repair.deposit` and rejects a positive amount when cumulative stored scoped case deposits plus that amount exceed the accepted frozen scope total (409 `DEPOSIT_EXCEEDED`), atomically with case/version, deposit, key, audit and outbox. Distinct keys cannot bypass the cap; retry identical committed keys for the original result. `depositRequired` is only the minimum to start, not the maximum funding ceiling: start still fails `DEPOSIT_REQUIRED` below that minimum, but funding up to the frozen total is allowed. Existing overfunded accepted cases fail closed on new case transitions, including execution, QC, return and billing; no automatic historical rewrite, refund, reallocation or guessed remediation is performed. Read access and already committed idempotent receipts remain available. Billing retains the defensive excess check. `POST /api/repair/invoices/:id/settle` `{expectedVersion,idempotencyKey,amount,currency,reference}` requires `repair.settle`, records operator payment, decrements exact remaining, rejects overpayment/currency mismatch/duplicate reference, and returns invoice. These additions do not make payment a precondition of the frozen return route.

- Lines: 1..100, exact keys `description,quantity,uom,unitPrice,currency`; description nonblank up to 200 characters, preserved as submitted. UOM is an exact uppercase string matching `[A-Z][A-Z0-9_]{0,15}` (caller-defined, no conversion/catalog inference).

After successful conversion, an identical authorized retry returns the same SO even after expiry or version advancement, without a second audit or outbox row. Changed payload with the same key is 409; a different key cannot reconvert an already converted quote. Six concurrent identical requests are tested. Unique indexes enforce one SO per scoped quote and one conversion per scoped key. | POST `/conversations/:id/mode` | cs.conversation.handoff | `{expectedVersion,toMode:BOT_ACTIVE|PAUSED|CLOSED,reason,commandKey}` |
| POST `/deliveries/:id/resolve` | cs.delivery.review | `{resolution,evidence,providerMessageId?,commandKey}` for UNKNOWN deliveries only |

Not exposed: `claimNextDelivery`, `recordDeliveryResult`, `reconcileExpiredSending` (trusted dispatcher), customer-principal methods or fixture/admin provisioning. Owner has read/write/note/handoff/review/reopen/reply actions; `csViewer` has read, `csAgent` read/write/note/handoff/reply, `csReviewer` read/review. `csFixtureAdmin` is harness-only. No provider send, QR or WhatsApp occurs here; delivery resolution is evidence-based operator bookkeeping. Public updates append customer-visible ticket history; replies queue outbound records, not sends.

All three paginated CS reads return `{data: [...], page: {limit, nextCursor}}`. Pass the opaque `nextCursor` unchanged (URL-encoded); null ends traversal. Unknown query fields, malformed cursors or limit outside 1..100 return 400. Ticket filters are `stage` and `assignee` (UUID or `unassigned`); conversation filter is `mode`. Conversation rows contain `{conversationId,mode,version,assigneeId,activeTicketId,customerLabel,lastActivityAt,hasUnknownDelivery}`. Thread rows contain `{messageId,direction,origin,kind,text,state,at}`; origin is CUSTOMER/BOT/SYSTEM/OPERATOR. Internal notes are excluded. Takeover is required before operator reply; resume uses the existing mode endpoint with BOT_ACTIVE. Mutations require the existing cookie, trusted Origin and JSON policy.

### Wave2d authoritative order reader

`initializeCustomerService` injects `src/order-reader.mjs` by default, reading a snapshot-consistent CRM account + sales order + work orders + shipment set on the real owned portfolio DB. CS `customerId` must equal the CRM account `_id` in the same tenant and plant; the sales order must belong to that account. Missing/foreign account or order returns null (CS NOT_FOUND). The package validates principal/binding before invoking the reader; revoked bindings are DENIED. Reader exceptions, timeout (default 2000ms), stale `asOf` (default 60000ms) map to STATUS_UNAVAILABLE; never a guessed stage.

New SO conversion stores `orderNumber` `SO-` plus 16 uppercase hash digits, stable across retries and enforced unique per tenant+plant. It is returned by existing SO list/detail reads; it is not the raw UUID. Pre-Wave2d orders without an orderNumber are not silently migrated or guessed. Public snapshot fields are only `{orderNumber,publicStage,progress,source,sourceId,sourceVersion,asOf}`; source is PORTFOLIO_API_OWNED and sourceId is opaque SHA-256. sourceVersion is SO version + sum of WO versions + committed shipment count, increasing across current append/versioned domain mutations. progress is null before planning, otherwise `{released,total}` counts WOs (released means no longer PLANNED).

Stage precedence: any shipment => PARTIALLY_SHIPPED, or SHIPPED if every SO line is fully shipped; otherwise any quarantined WO => QUALITY_INSPECTION, any IN_PROGRESS => PRODUCTION, any QC_COMPLETED => READY_TO_SHIP, remaining planned/released WOs => PLANNING, no WOs => ACCEPTED. For mixed WOs, quality/production take precedence over ready. CS reports `liveLookup:true`, source/version/asOf; fixtures are never the default. The trusted initialize option `{customerService:{allowSyntheticOrders:true}}` explicitly selects the old synthetic fixture path for legacy tests only; no HTTP switch exists.

### Wave2d ledger semantics and reconciliation reads

Every shipment appends one immutable scoped `warehouseMovements` SHIP row per source in its existing snapshot/majority transaction: receipt counters, reservation state, source/SO tallies, shipment row, key, audit and outbox either all commit or all roll back. Movement fields include tenantId, plantId, shipmentId, salesOrderId, accountId, lineIndex, sourceType/sourceId, quantity string and UOM. Reservation source: RESERVED -> SHIPPED with receiptId/reservationId; WO source: QC_ACCEPTED_OUTPUT -> SHIPPED with workOrderId and **no raw-material receiptId**. WO shipment does not alter raw-material receipt balances. No HTTP update/delete movement route exists; replay returns the saved result and appends nothing.

Reservation states: RESERVED initially, PARTIALLY_SHIPPED after partial use, CONSUMED after full use. Original quantity is retained; shippedQuantity/remainingQuantity and version advance atomically. Partial reservations remain shippable; consumed ones are refused. Both source kinds require the same SO/line/account and selected tenant/plant. Source tally ceilings prevent overconsumption; competing different keys serialize on the transaction fences/tallies.

- GET `/api/warehouse/receipts/:id/reconciliation` (warehouse.read): `{receiptId,uom,replayed,cached,matches,warehouseMovementCount,materialMovementCount}` in data. Replays warehouse PUTAWAY/RESERVE/SHIP plus manufacturingMovements MATERIAL_RESERVED/MATERIAL_CONSUMED from a single read snapshot. Counters: availableQuantity, reservedQuantity, shippedQuantity, manufacturingReservedQuantity, manufacturingConsumedQuantity. RECEIVE/QC_RELEASE describe pre-storage quarantine/released transit, not these cached five storage/disposition counters. MATERIAL_RESERVED removes available and adds manufacturing reserved; MATERIAL_CONSUMED moves that reserve to consumed. WO finished output is a separate stream, never counted as raw material.
- GET `/api/fulfillment/orders/:id/reconciliation` (fulfillment.read): `{salesOrderId,lines,sources,shipmentCount,movementCount,matches}`. Lines compare SO shipped tally, shipment sum and SHIP movement sum in exact decimal quantities/UOM; sources compare source tally and movement sum, and each shipment's stockMovementCount must match its movements. A mismatch is reported, never automatically repaired.
- Existing UI fulfillment GETs are complete: `/api/fulfillment/shipments`, `/invoices`, `/payments` plus `/:id` detail; lists accept limit 1..100 (default 25) and UUID cursor, returning the usual data/page envelope. `/api/fulfillment/orders/:id/balances` returns currency and per-line ordered/shipped/invoiced quantities with UOM. Invoice detail contains fixed-scale total/paid/outstanding amounts and currency; payment detail contains fixed-scale amount/currency and allocations. These are operator-recorded bookkeeping, not provider settlement.

## Wave3 bounded repair contract

Paths start `/api/repair`. Existing contracts remain unchanged except an internal optional `repairFence` counter on quotes read for repair scope/decision; public quote version and snapshots are unchanged. Same cookie, Origin/JSON, alias, errors and UUID pagination policies apply. GET `/cases`, `/invoices`, `/deposits` and each `/:id` require `repair.read`; invoice/deposit records are real scoped persisted documents, not fulfillment records. POST `/cases` requires `repair.intake`, returns 201 `{data:case}` for `{accountId,serial,condition,currency,idempotencyKey}`. Account must exist in the selected scope. Owner is permanently `ownerAccountId`; no inventory receipt, ownership transfer or resale stock is created.

Every transition is POST `/cases/:id/<action>`, returns 200 `{data:case}`, and requires `{expectedVersion,idempotencyKey,...}`. Versions start at 1 and advance once per committed command. Additional fields:

| action (permission `repair.<action>`) | Fields | State boundary |
| --- | --- | --- |
| diagnostic-authorize | feeCap,evidence | INTAKE -> DIAGNOSIS_AUTHORIZED |
| teardown | findings:[{component,disposition}],evidence | authorized -> TEARDOWN |
| scope | quoteId,revision,depositRequired,evidence | TEARDOWN or SCOPE_QUOTED -> SCOPE_QUOTED; append immutable local scope revision |
| decide | decision:ACCEPT or REJECT,revision,evidence,diagnosticFee (REJECT only) | SCOPE_QUOTED -> AUTHORIZED or REJECTED |
| deposit | amount,currency,reference | AUTHORIZED only; records an internal receipt, not provider settlement |
| start | no extra fields | AUTHORIZED -> IN_PROGRESS only after persisted deposit sum covers frozen requirement |
| execute | dispositions:[{component,disposition}],evidence | IN_PROGRESS -> TESTING; exact component/disposition set must match scoped findings |
| test | result:PASS or FAIL,evidence | TESTING -> TEST_PASSED or REWORK |
| rework | evidence | REWORK -> TESTING; immutable failed-run reference |
| hold | active:boolean,evidence | append hold/release evidence; terminal RETURNED forbidden |
| qc | evidence | TEST_PASSED -> READY_FOR_RETURN, only latest passing test and no active hold |
| return | evidence | READY_FOR_RETURN or REJECTED -> RETURNED, no active hold; custody changes only here |

All evidence/serial/condition/reference/component strings are trimmed, nonblank, max 1000. Findings/dispositions have 1..100 unique component names, disposition REPAIR/REPLACE/REUSE/SCRAP, exact nested keys only. Their recording is operator evidence, not stock/material consumption, telemetry or hardware verification. A failed test cannot be followed by another test without committed rework. Holds prevent QC and either return branch, but do not freeze diagnostic or repair recording. Last explicit hold/release is authoritative; this is not the legacy multi-entity hold system or maker/checker segregation.

Scope uses an existing latest unexpired APPROVED or ACCEPTED commercial quote revision for the same scoped account/currency, copies its approval snapshot, and freezes findings/deposit requirement. `scope.revision` is the repair-local append number; `quoteRevision` preserves the source number. `decide.revision` is the repair-local number. Requoting is allowed only before decision; previous scope remains immutable. Decision rechecks source latest revision/state/expiry and writes a quote fence to serialize concurrent revision/conversion. Internal ACCEPT recording is customer authorization evidence, not external signature and does not alter commercial quote acceptance or create an SO. No post-authorization scope extension endpoint exists.

Money uses the existing currencies/scales (USD/EUR/GBP/IDR=2, JPY=0, KWD=3), canonical decimal strings up to 28 integer digits, BigInt minor units, no FX/Number conversion. Deposit requirement cannot exceed quote total. Positive deposit records bind case/account/currency; duplicate reference on a case conflicts. Start sums stored `repairDeposits` inside its transaction, never a supplied paid flag. Deposits are currently unapplied internal prepayments; no final repair billing/application/refund/settlement endpoint is claimed. Rejected scopes atomically issue one `repairInvoices` DIAGNOSTIC NO_TAX snapshot (quantity `1`, UOM `EA`, total=fee) bounded by authorized feeCap, including a zero-value invoice if fee is zero. `remaining` initially equals total, with no settlement endpoint yet. Rejection releases but does not return custody. Evidence-backed return records RETURNED_UNREPAIRED_TO_CUSTOMER or RETURNED_TO_CUSTOMER; customer ownership remains unchanged.

Case holds append-only-by-API custody/history/scopes/tests/reworks/holds and records actors/times. Collections `repairCases`, `repairDeposits`, `repairInvoices`, `repairKeys`, `repairAudit`, `repairOutbox` commit together with live session/membership/role/entity write fences. Every non-replay adds one audit and one PENDING outbox row (`repair.<action>`, intake `repair.intake`), no external worker. Key 8..100 `[A-Za-z0-9_-]`, tenant+plant scoped across all repair actions, hashes recursively sorted body plus action/target. Authorized identical retry returns original committed response even after version/state advancement; changed payload conflicts. No privileged-direct-writer immutability claim. Bad input 400; missing/foreign reference 404; scope/role denied 403; version/state/cap/funding/currency/key conflicts 409.

Owner receives all repair permissions. `repairRead`, `repairIntake`, `repairDiagnosticAuthorize`, `repairTeardown`, `repairScope`, `repairDecide`, `repairDeposit`, `repairStart`, `repairExecute`, `repairTest`, `repairRework`, `repairQc`, `repairHold`, `repairReturn` each grant read plus only the named action. Advisory session capabilities are unchanged. Real owned Mongo/HTTP test: `node --test --test-reporter=tap test/repair.test.mjs`; validators prove audit/outbox rollback and exact response replay, with decimals, tenant, role/revocation, stale version and concurrent identical commands. This is a bounded mounted API slice, not full E02 parity: no repair SO/work-order integration, material/labor stock ledger, tax policy, final invoice/deposit application, diagnostic settlement, carrier/POD verification, warranty, UI, OS-kill/restart repair proof or production authority migration.
