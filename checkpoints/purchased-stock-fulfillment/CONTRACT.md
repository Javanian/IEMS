# Purchased stock fulfillment: contract for freeze

Baseline 692463a7. Status: FROZEN by lead for this bounded implementation. Existing legacy and manufactured flows remain unchanged and unsupported by this adapter. Existing mixed typed SOs may fulfill PURCHASED lines only; MANUFACTURED lines remain explicitly blocked. No description matching, legacy adoption, synthetic WO, new availability ledger, or F5 fence change.

## Authority and bounds

Use the SAME catalogMaterialReservations, catalogMaterialReservationRevisions, catalogUseHeads and catalogUseEvents as internal execution. Immutable catalogStockBalances/catalogStockUnits, receipt/origin/QC/putaway proof remain unchanged. Customer rows have schema CATALOG_CUSTOMER_RESERVATION_V1, demandKind SALES_ORDER_LINE, sourceKind CATALOG_RECEIPT. Unmarked existing production rows retain their exact contract; unknown/coherently stripped customer markers are rejected through independent consumer/history evidence.

One purchasedFulfillmentHeads row per scoped SO (_id=SO UUID) provides real line-demand CAS, with immutable purchasedFulfillmentEvents. Virtual version1 precedes first mutation. SO itself is never given a hidden useFence because its whole-row quote proof is immutable. Source common catalogUseHeads CAS plus actual receipt version/fence serializes production and customer use. Existing stock unit rows are immutable; expectedStockVersion is the shared mutable custody version for selected units. No invented per-unit mutable version.

Maximum100 total claims per receipt,100 per SO (including released history),400 shared source events/history,400 consumer events,100 shipments per SO,100 typed invoices and100 typed payments per SO,20 reservation sources per shipment and100 selected SERIAL units per shipment. Overflow refuses without effects; no silent truncation. LOT quantity is positive exact decimal up to six fractional places; SERIAL quantity integral and equal to the actual selected identity count. Caps are implementation bounds, not capacity certification.

Shared balances: onHand=openingAccepted-productionConsumed-customerShipped; available=openingAccepted-productionReserved-productionIssued-productionConsumed-customerRemainingReserved-customerShipped. No second raw consumption, issue or manufacturing output for customer dispatch. Opening rejected units never become eligible. New shippedQuantity is exposed separately once customer-use evidence exists. Existing legacy receipt quantity counters remain zero for typed stock.

Customer row quantities obey quantity=remainingQuantity+shippedQuantity+releasedQuantity. Transitions: RESERVED -> PARTIALLY_SHIPPED (repeat allowed) -> SHIPPED, or release ALL remaining -> RELEASED (including after partial dispatch). Actual shipped unit IDs/serials are terminal and never freed. RELEASED retains already shipped quantity/identities, releases only the unshipped remainder, and may occur under holds/master/location withdrawal if historical proof is valid.

Fresh reserve/ship requires validated current selected PURCHASED SO binding, item/revision/version/contentHash/UOM/owner match to the actual receipt source, current approved master, approved accepted-only stock, qualified company location/bin, no strict live hold/malformed hold cache, and real master/location/bin/receipt/source-head fences. Other unsupported or stale SO lines do not poison an independently eligible PURCHASED line. Later withdrawal does not erase actually shipped history: POD, invoicing and settlement use historical shipment/source proof, without fresh stock eligibility checks.

## Actions and registration

New catalog.stock.reserve and catalog.stock.ship actions; retain catalog.stock.read. Roles purchasedFulfillmentReader=[fulfillment.read,catalog.stock.read], purchasedFulfillmentReserver=[those reads,catalog.stock.reserve], purchasedFulfillmentShipper=[those reads,fulfillment.ship,catalog.stock.ship]. Existing invoice/payment/delivery roles retain their own actions; no quote.read or master.read prerequisite for this adapter. Reads require BOTH fulfillment.read and catalog.stock.read. Reserve/release guards catalog.stock.reserve AND fulfillment.read; dispatch guards catalog.stock.ship AND fulfillment.ship, inside transaction before durable keys. No two-person separation claim.

Exports from purchased-fulfillment.mjs: initializePurchasedFulfillment(db), installPurchasedFulfillment(app,runtime,{fail,guard,id,fields}), purchasedFulfillmentActions, purchasedFulfillmentRoles. The backend lane registers these in app.mjs. Existing POD/fulfillment receive narrow typed-proof adapters only; the blanket legacy fallback is never opened for typed orders.

## Routes and exact request bodies

Prefix /api/purchased-fulfillment. Existing scope aliases remain supported; caller cannot supply owner, snapshots, hashes, source kind, eligibility or statuses.

GET /orders?cursor=&limit=: ordinary {data:[summary],page:{limit,nextCursor}}, ascending SO UUID. Only independently proven catalog SOs. Summary {_id,orderNumber,accountId,status,version:SOversion,purchasedLineCount}; no browser all-pages fallback needed. default25,max100, strict UUID cursor.

GET /orders/:salesOrderId: {data:view}, snapshot read with no writes. Unknown/foreign404. Typed quote/SO historical validation is mandatory; unbound or unsupported-schema SO409 PURCHASED_ORDER_UNSUPPORTED. Mixed typed order is readable; unsupported lines are marked.

POST /orders/:id/reservations body:
{expectedVersion,expectedSalesOrderVersion,lineIndex,receiptId,expectedReceiptVersion,expectedStockVersion,quantity,unitIds?,reason,idempotencyKey}

expectedVersion is the purchased SO-demand head version (initial1); expectedSalesOrderVersion is actual frozen SO version. SERIAL requires explicit nonempty unique actual catalogStockUnits UUIDs; server derives serial labels. LOT unitIds absent or[] only; null rejected. Returns200 full view. Multiple reservations from one receipt or repeat reserve after release are allowed within shared caps; history stays append-only.

POST /orders/:id/reservations/:reservationId/release body:
{expectedVersion,expectedReservationVersion,expectedReceiptVersion,expectedStockVersion,reason,idempotencyKey}

Releases ALL remaining unshipped quantity/units, preserves immutable shipped part; zero remainder409 STATE_CONFLICT. Returns200 full view.

POST /orders/:id/shipments body:
{expectedVersion,expectedSalesOrderVersion,lineIndex,reference,reason,sources:[{reservationId,expectedReservationVersion,expectedReceiptVersion,expectedStockVersion,quantity,unitIds?}],idempotencyKey}

All sources belong to this SO and selected line; unique reservation IDs, max20. SERIAL unitIds are explicit unshipped UUID subset of that reservation; LOT absent/[] only. Partial quantities supported. Returns201 the actual persisted fulfillmentShipments row (plus derived purchasedProof metadata if documented by provider), with schema PURCHASED_SHIPMENT_V1 and sources[{sourceType:CATALOG_RESERVATION,sourceId:reservationId,receiptId,quantity,unitIds:[UUID],serials:[actual strings] only for SERIAL,materialTrace:{receiptId,lotNumber?,heatNumber?},...immutable source proof pointers}]. No WORK_ORDER source or fake legacy warehouseReservation. Actual new stock movements belong only to the dedicated catalogCustomerShipments ledger. Typed POD/reconciliation explicitly load and validate that ledger; no warehouseMovements SHIP projection is created, and legacy receipt counters remain zero. The immutable receipt/origin/QC validator therefore keeps its prohibition on non-RECEIVE legacy warehouse effects. Shipment stockMovementCount=sources.length.

GET /orders/:id/events?cursor=&limit=: full immutable event rows, ordinary UUID cursor/default25/max100 pagination after bounded whole-current-authority validation. Each row {_id,salesOrderId,version,kind,reason,recordedBy,recordedAt,snapshot,contentHash}. Technical IDs/hashes/actors remain Audit UI data.

Existing /api/catalog-stock/receipts?itemId=&itemRevision=&q=&cursor=&limit= and /receipts/:id are the authoritative source picker/detail under catalog.stock.read. Option rows preserve receiptId,receiptVersion,version(sharedStockVersion),source,receipt,opening,onHandQuantity,reservedQuantity,issuedQuantity,consumedQuantity,availableQuantity,eligibleQuantity,units[{_id,version:immutableOpeningVersion,serial,openingStatus,status,eligible,...}],sourceHolds,blockers,canAllocate. Customer-use rows additionally expose shippedQuantity. Do not infer claimable units from receipt.serials; use units[]. UUID selection must use _id. Existing receiptId-page cursor semantics remain unchanged, including empty filtered pages with nextCursor.

## View

{schema:PURCHASED_FULFILLMENT_V1,salesOrder:validatedActualSO,version:consumerHeadVersion,sourceHash:immutableOrderHash,lines:[{lineIndex,description,quantity,uom,catalogBinding,supported,blockers:[code],reservedQuantity,shippedQuantity,releasedQuantity,invoicedQuantity,remainingReserveQuantity,remainingShipQuantity,canReserve,canShip}],reservations:[row plus canRelease,remainingUnitIds],stockSources:[current actual referenced catalog stock views],shipments:[actual validated typed shipments],canReserve,canShip,authorityHash:null|string}.

Row fields: _id,version,contentHash,schema,demandKind,sourceKind,salesOrderId,salesOrderVersion,lineIndex,receiptId,originHash,openingBalanceHash,itemId,itemRevision,uom,ownerLegalEntityId,quantity,serials,unitIds,shippedQuantity,releasedQuantity,remainingQuantity,shippedUnitIds,status,sourceSnapshot,previousHash,recordedBy,recordedAt. SourceSnapshot freezes actual origin.source, locationSnapshot, lotNumber/heatNumber or null and immutable units[{unitId,registryId,serial,contentHash}]. The sibling row fields orderHash and bindingHash bind the frozen quote/order line authority; they are not fields inside sourceSnapshot. No caller source kind or fabricated executionId/materialLineId.

reservedQuantity is remaining active reserved for that SO line; shippedQuantity includes irreversible shipments even if a claim later releases its remainder; remainingReserveQuantity=ordered-shipped-activeReserved; remainingShipQuantity=activeReserved. Released history is shown but does not reduce future demand capacity beyond its already shipped portion. Flags are server-authoritative action readiness, not permission grants; UI also checks actual action grants.

## POD and money

Existing actual routes remain /api/deliveries/shipments/:id[/confirmations], /api/fulfillment/invoices and /api/fulfillment/payments, with existing bodies/response statuses. SERIAL purchased source proof is validated against actual catalog unit/reservation/shipment ledger, not manufacturingOutputUnits. Invoice sources must be actual independently proven purchased shipments for the selected typed lines; payments must reference actual proof-bound typed invoices. Current item/hold/location withdrawal after dispatch does not deny coherent historical POD/billing; corruption does. A payment may allocate across proven purchased invoices of ONE typed SO only; mixing typed and legacy invoices or multiple typed SOs is rejected409 PURCHASED_FULFILLMENT_MODE_CONFLICT. Pure legacy payments retain the old workflow. No service milestone, deposit, return, amendment or cross-plant feature added.

Typed financial replay validates the independent shipment/invoice/payment proof after current action guard and before key return; no raw mutable source/key.result trust. Existing cumulative exact money/tax caps and real source/tally CAS remain. Invoice/shipment document preparation validates typed proof before existing financial renderer mapping; PDFs remain financial/delivery documents, not standalone catalog-identity certificates. Issued invoice proof stores the full initial invoice; each actual payment proof binds its immutable payment plus previous/current FULL invoice snapshots, including version, status, paid/outstanding amounts, allocations and updatedAt. Validate this exact version/hash chain against the current invoice, excluding only documentFence; do not discard settlement fields to fit the initial invoice hash. Dedicated purchasedShipmentProofs/purchasedInvoiceProofs/purchasedPaymentProofs independently classify typed history even if markers/heads are stripped. Exclude ONLY documented technical documentFence/deliveryUseFence from immutable shipment semantics, never business fields.

## Keys, errors and proof

Every new command uses idempotencyKey 8..100 ASCII letters/digits/underscore/hyphen and reason trimmed3..1000. Reserve/release POST returns data as the CURRENT validated full view plus data.commandReceipt={kind,salesOrderId,version,reservationId,reservationVersion,reservationHash}. This immutable command receipt is anchored by commandProof.resultHash in the immutable consumer event/key and is identical on exact replay; the surrounding view is current, not a historical response snapshot. GET does not include commandReceipt. Shipment POST/replay returns the immutable actual shipment business snapshot (documentFence/deliveryUseFence excluded), anchored by a shipment command receipt and independent physical proof. Exact replay reauthorizes all actions, validates frozen proof/receipt, and returns these documented results; it does not require withdrawn sources to become freshly eligible. Changed payload409 IDEMPOTENCY_CONFLICT. Reserved key namespaces cannot shadow legacy fulfillment keys. Successful command replay still advances the existing authorization fences per guard (two-action commands increment each of the six exact current authorization crmFence fields by2); no stock/demand/business duplicate effect. Rejections roll back ALL writes, including fences. GET writes nothing.

400: existing UNKNOWN_FIELD/INVALID_ID/INVALID_VERSION/INVALID_QUANTITY/INVALID_PAGINATION; INVALID_UNITS for malformed or duplicate/incorrect policy unit selections. 404 NOT_FOUND unknown/foreign identity. 403 existing SCOPE_DENIED/UNAUTHENTICATED policy. 409: VERSION_CONFLICT stale versions; STATE_CONFLICT invalid transition; INSUFFICIENT_STOCK exceeds source availability; QUANTITY_EXCEEDED exceeds SO line or reservation remaining; PURCHASED_ORDER_UNSUPPORTED unbound/cohort-ineligible SO; PURCHASED_LINE_UNSUPPORTED non-PURCHASED line; PURCHASED_ITEM_CHANGED fresh SO binding/source mismatch; STOCK_ENCUMBERED strict source hold; CATALOG_DEPENDENCY_CHANGED withdrawn item/location; PURCHASED_FULFILLMENT_SOURCE_INVALID malformed/orphan customer/dispatch/financial proof; existing QUOTE_SOURCE_INVALID/CATALOG_STOCK_SOURCE_INVALID for their authority domains; STOCK_HISTORY_LIMIT or FULFILLMENT_HISTORY_LIMIT bounded history overflow.

New collections: purchasedFulfillmentHeads, purchasedFulfillmentEvents, purchasedFulfillmentKeys, purchasedFulfillmentAudit, purchasedFulfillmentOutbox, catalogCustomerShipments, purchasedShipmentProofs, purchasedInvoiceProofs, purchasedPaymentProofs. Shared stock claims/history/head remain in the existing catalog collections. New dedicated source-bearing collections store sourceReceiptIds with scoped indexes, or receiptId with its scoped physical-ledger index. Actual rows in the existing fulfillmentShipments, fulfillmentInvoices, fulfillmentPayments and fulfillmentKeys collections also retain sourceReceiptIds, but this increment adds no dedicated sourceReceiptIds index to those existing collections. Absence checks include them without claiming selective indexed scans or maximum-capacity performance. Missing shared head plus ANY surviving consumer/financial/physical evidence must fail closed, not reset opening availability. Historical source snapshots, consumer head refs, common head refs, reservation history and actual shipment movement/typed proof are cross-checked; self-rehashed pointers cannot silently redirect a unit/source.

Controlled CAS test seam: existing catalogStockContext + writeCatalogReservation handle both authentic production and customer reservation row variants; exported validated customer context/writer will permit two owned transactions to attempt real stored claim releases, then abort BOTH. This isolates shared source CAS from HTTP authorization serialization without weakening production authorization. Separately test actual authorized HTTP competing stock claims and retain all revocation fences/F5 BLOCKED.

Readiness reflects history budgets: source version401 disables further source writes with STOCK_HISTORY_LIMIT; consumer version401 disables new reserve/ship/release with FULFILLMENT_HISTORY_LIMIT. Reaching100 claims blocks new claims while existing claims may still ship or release within event budgets. Reaching100 shipments blocks new reservations/shipments, while remaining claims may release. These limits preserve readable proof histories; positive maximum-load capacity has not been certified. Typed balances, entitlement and reconciliation reads validate actual shipment, immutable invoice/payment histories and both shipment/SO billing tallies in the same snapshot. Dedicated catalogCustomerShipments are the typed movement ledger; warehouse SHIP records remain absent.
