## Required customer-work-order labor

An optional nonempty unique `requiredLaborOperationIndices` list selects routing operations that require actual labor entries before their operation records. Indices are sorted and bounded0..49; release rejects absent routing indices. Each required entry belongs to the authenticated operator, scoped work order and actual operation; its positive exact elapsed milliseconds must equal the reported UTC window. Optional positive integer `activeDurationMs` distinguishes productive time from a longer window with breaks: at most24 active hours within at most7 elapsed days. Without that explicit field the prior24-hour window limit remains. Operator-overlap checks and transactional authority fencing remain active.

Required entries are revalidated before output QC; missing or malformed proof cannot release output. The work order retains labor-entry references and elapsed/active durations. Work orders without the opt-in list preserve their previous contract. The four original E01 sessions total45 active hours and bind to two actual scoped synthetic operator identities. Additional routing operations are explicitly supplemental evidence; no employee payroll or machine telemetry proof is inferred.

## Controlled delivery/POD

Separate shipment dispatch from delivery confirmation. Existing shipment, stock movement, output identity and billing entitlement remain authoritative and unchanged. GET `/api/deliveries/shipments/:id` requires fulfillment.read. POST `/api/deliveries/shipments/:id/confirmations` requires the dedicated fulfillment.deliver capability, rechecked transactionally before idempotent replay. Owner receives it; old shipper/reader roles do not. Dedicated role fulfillmentDelivery includes read and deliver. History GET supports deterministic UUID cursor pagination.

Command body: expectedVersion (virtual delivery head1), expectedShipmentVersion, exact positive quantity, deliveredAt (reported UTC ISO instant between dispatch and current business time, with five-minute clock tolerance), receiverName, receiverReference, evidenceReference, evidenceNotes, idempotencyKey. Shipments with tracked outputs require explicit unique actual shipped serials. Any quantity beyond their count consumes only the original untracked shipment budget; an explicit empty array may confirm just that budget in a mixed shipment. Fully serialized quantities therefore require an exact serial count. Fully untracked shipments reject a serials field. Receiver/evidence text is operator-entered evidence, not independent signature or carrier verification. Partial confirmation is allowed up to remaining shipped quantity, at most100 immutable confirmation records. No inference of missing identities, no stock restoration or re-dispatch. Delivery status is NOT_DELIVERED/PARTIALLY_DELIVERED/DELIVERED independently of the shipment's SHIPPED status.

Each fresh confirmation uses actual scoped shipment/sole matching source SHIP movements/output references, shipment use fence, delivery-head CAS, immutable confirmation/event hashes, idempotency key, audit and outbox in one transaction. Exact replay returns the original committed view only after fresh authorization; changed key reuse conflicts. Orphan or tampered delivery evidence fails closed. Delivered quantity/serial sets exactly equal immutable evidence; failed/stale/foreign/revoked/oversized commands have no domain effects. Historical shipment source is conserved; later holds do not rewrite a dispatched shipment or prevent recording its actual delivery evidence.

## Source picker

New catalog options require scoped catalog.read and source-specific master.read or procurement.read. Items use explicit PURCHASED_V2_APPROVED eligibility; vendors use ACTIVE_VENDOR. Search is bounded escaped prefix text, <=80 characters, with default25/max100 page size. Scoped UUID ascending cursor ordering is deterministic and unique on a stable dataset. Newly inserted earlier IDs can require restarting the search; the response documents live-page semantics. Selected IDs hydrate separately even outside the active page; current source eligibility/version/revision must be visible and reselected when invalid. Server validates mutations again. The UI aborts/ignores obsolete searches and preserves selections across pages/revisions. Query-plan and250+ records beyond-page proof are required before F4 acceptance.
